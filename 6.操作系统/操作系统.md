# 01 基础概念

## 什么是操作系统？

操作系统是管理计算机硬件和软件资源的系统软件，向上对用户程序提供接口，向下接管硬件资源。本质上是运行在硬件之上的第一层软件，负责处理器管理、存储器管理、设备管理、文件管理。

## 操作系统分类

| 类型 | 特点 | 例子 |
|------|------|------|
| 批处理系统 | 作业成批处理，无交互 | 早期大型机 |
| 分时系统 | 多用户轮流使用CPU时间片 | Unix |
| 实时系统 | 必须在规定时间内响应 | 车载系统、航天 |
| 通用系统 | 兼顾批处理和分时 | Windows、Linux、macOS |

## 内核态与用户态

```
用户态 ── 用户程序运行。不能执行特权指令，只能访问用户地址空间
内核态 ── 操作系统内核运行。可执行一切指令，访问所有内存

为什么要有这两种状态？
  → 防止用户程序破坏操作系统和关键数据
```

**切换方式：**
1. **系统调用**：用户程序主动请求OS服务（软中断）
2. **异常**：错误引起（缺页、除零等）
3. **外部中断**：硬件信号通知（键盘、时钟、网卡）

## 并发 vs 并行

```
并发 (Concurrency)：
  单核CPU，宏观"同时"，微观交替执行
  线程A: ██░░██░░██░░
  线程B: ░░██░░██░░██

并行 (Parallelism)：
  多核CPU，物理上真正同时执行
  核1: ████████████
  核2: ████████████
```

# 02 进程

## 进程是什么？

**进程 = 运行中的程序实例。** 是资源分配的基本单位。

```
一个进程由三部分组成：
┌─────────────────┐
│ PCB (进程控制块) │ ← 进程唯一标识，含PID、状态、优先级、CPU现场
├─────────────────┤
│ 程序段 (代码)    │ ← 可执行指令
├─────────────────┤
│ 数据段 (堆+栈)   │ ← 运行时数据
└─────────────────┘
```

## 进程的三种基本状态

```
         时间片用完
    ┌─── 就绪 ──────────→ 运行 ───┐
    │     ↑                    │
    │     等待事件发生            │ 等待事件(IO等)
    │     │                    ↓
    │     └─────── 阻塞 ←──────┘
    │
    └── 被调度选中 ────→
```

| 状态 | 含义 |
|------|------|
| **运行态** | 正在使用CPU |
| **就绪态** | 可以运行，等CPU空闲 |
| **阻塞态** | 等待某事件（IO等），不能运行 |

## 进程调度策略

| 算法 | 思路 | 特点 |
|------|------|------|
| FCFS 先来先服务 | 按到达顺序 | 简单，短作业可能等很久 |
| SJF 短作业优先 | 优先执行最短的 | 平均等待时间最短，但长作业可能饿死 |
| 优先级调度 | 优先级高的先运行 | 可能低优先级饿死 |
| 时间片轮转 RR | 每人轮流运行一段时间片 | 公平，交互性好 |
| 多级反馈队列 | 多队列 + 优先级 + 时间片 | **最复杂但效果最好，Linux/Windows使用** |

## 进程间通信 IPC

**为什么需要IPC？** 每个进程有独立的地址空间，互相看不到对方的数据。

| 方式 | 原理 | 特点 |
|------|------|------|
| **管道** | 内核缓冲区，一端写一端读 | 有血缘关系进程间，半双工 |
| **消息队列** | 内核中的消息链表 | 无血缘限制，异步 |
| **信号量** | 计数器，控制多进程对共享资源访问 | 用于同步互斥 |
| **共享内存** | 多个进程映射同一物理内存 | **最快！** 但需自己同步 |
| **Socket** | 网络通信 | 跨机器，最通用 |

## 孤儿进程与僵尸进程

| | 孤儿进程 | 僵尸进程 |
|---|---|---|
| 定义 | 父进程先于子进程退出 | 子进程退出，父进程未调用wait回收 |
| 后果 | 被init(1号进程)收养，无害 | 占用PCB，积累多了导致无法创建新进程 |
| 解决 | - | 父进程调用 `wait()`/`waitpid()`，或忽略SIGCHLD信号 |

# 03 线程

## 线程是什么？

**线程 = 进程内的执行流。** 是CPU调度的基本单位。

```
一个进程可以有多个线程：
┌─────────────── 进程 ───────────────┐
│  ┌──────┐ ┌──────┐ ┌──────┐      │
│  │线程1 │ │线程2 │ │线程3 │      │ ← 每个线程独立调度
│  └──────┘ └──────┘ └──────┘      │
│  共享：代码、数据、堆、打开文件      │
│  独立：栈、寄存器、PC              │
└────────────────────────────────────┘
```

## 进程 vs 线程

| | 进程 | 线程 |
|---|---|---|
| **资源** | 资源分配基本单位 | CPU调度基本单位 |
| **地址空间** | 独立 | 共享进程的地址空间 |
| **通信** | IPC（管道、共享内存等），慢 | 直接读写共享变量，快 |
| **切换开销** | 大（页表切换、缓存刷新） | 小（只需切换寄存器） |
| **崩溃影响** | 一个进程崩溃不影响其他 | **一个线程崩溃 → 整个进程崩溃** |
| **创建开销** | 大 | 小 |

## 多线程模型

| 模型 | 用户线程 : 内核线程 | 特点 |
|------|-------------------|------|
| 多对一 | N : 1 | 一个阻塞全部阻塞，已淘汰 |
| **一对一** | 1 : 1 | 并发性好，Linux/Windows 使用 |
| 多对多 | N : M | 折中方案 |

## 为什么需要线程？

1. 进程同时只能做一件事 → 多线程可**并发执行多个任务**
2. 进程阻塞整个挂起 → 一个线程阻塞不影响其他线程
3. 线程创建/切换开销远小于进程
4. 线程间共享地址空间，通信简单

# 04 线程池

## 什么是线程池？

**线程池 = 预先创建好一批线程，有任务就分配，用完放回，不销毁。**

```
没有线程池时：           有线程池时：
  来任务 → new线程     来任务 → 从池里拿一个空闲线程
  用完  → destroy线程   用完  → 放回池里，不销毁
  来任务 → new线程     来任务 → 从池里拿一个空闲线程
  用完  → destroy线程   ...
  ↑ 频繁创建销毁，        ↑ 线程复用，无创建销毁开销
    开销巨大
```

## 为什么需要线程池？

1. **减少创建销毁开销**：线程创建（分配栈、初始化）和销毁都很贵
2. **控制线程数量**：防止无限制创建线程导致OOM或调度崩溃
3. **任务队列缓冲**：任务多时排队，不会瞬间打爆系统

## 线程池核心参数

```cpp
// 以通用线程池为例
ThreadPool:
  core_threads    // 核心线程数（一直存活）
  max_threads     // 最大线程数
  task_queue      // 任务队列（放不下时才创建新线程，直到max）
  keep_alive_time // 非核心线程空闲多久后被回收
  reject_policy   // 队列满且线程满 → 拒绝策略
```

## 游戏引擎中的线程池

UE 和 Unity 都使用 Job System + Worker Thread 模式：

```
主线程提交Job → Job队列 → Worker线程池取Job执行 → 主线程收结果
                    ↑
            不会频繁创建销毁线程
```

# 05 协程

## 协程是什么？

**协程 = 用户态的"轻量级线程"，由程序自己调度，不由操作系统调度。**

```
进程
 └── 线程（操作系统调度，内核态切换）
      └── 协程（用户代码调度，用户态切换）
           切换开销：线程 >> 协程

线程切换：用户态↔内核态，保存整套寄存器、栈
协程切换：纯用户态，只保存少量寄存器，更像函数调用
```

## 协程 vs 线程

| | 线程 | 协程 |
|---|---|---|
| **调度者** | 操作系统内核 | 用户代码（程序员/运行时） |
| **切换开销** | 大（~几微秒） | 极小（~几十纳秒） |
| **栈大小** | 通常 1~8 MB | 通常几 KB（可按需增长） |
| **数量** | 受限于内存和调度开销 | 可以轻松创建几十万个 |
| **抢占** | 抢占式（时间片到期强制切换） | 协作式（主动 yield 才切换） |
| **适用场景** | CPU 密集型 | **IO 密集型**（网络、文件） |

## 协程的应用

**C++（C++20）：**
```cpp
// 无栈协程（编译器生成状态机）
task<int> fetch() {
    auto data = co_await http_get("url");
    co_return data.size();
}
```

**C# / Unity：**
```csharp
IEnumerator LoadAssets() {
    yield return StartCoroutine(LoadPrefab());
    yield return new WaitForSeconds(1f);
}
```

**游戏服务端：** 用协程处理大量玩家连接（几万连接 → 几万个协程，而非几万个线程）。

# 06 并发与同步

## 为什么需要同步？

多个线程同时访问共享数据 → 数据竞争 → 结果不可预测。

```cpp
// 两个线程同时执行 counter++
// counter++ 其实是三步：
//   1. 读取 counter 到寄存器
//   2. 寄存器 +1
//   3. 写回 counter

线程A: 读(0) → +1(1) → 写(1)
线程B:       读(0) → +1(1) → 写(1)
// 预期 counter = 2，实际 = 1！
```

## 临界区与竞态条件

- **临界区**：访问共享资源的代码段，必须互斥进入
- **竞态条件**：多个线程的执行顺序影响最终结果

## 同步方式

| 方式 | 说明 |
|------|------|
| 互斥锁 (Mutex) | 保证同一时刻只有一个线程进入临界区 |
| 读写锁 | 允许多个读者，写者互斥 |
| 信号量 (Semaphore) | 控制同时访问资源的线程数量 |
| 条件变量 | 线程等待某个条件成立再继续 |
| 屏障 (Barrier) | 所有线程到达同一点后才继续 |

# 07 锁

## 互斥锁 (Mutex)

```cpp
// 最简单的互斥锁
std::mutex m;
m.lock();       // 获取锁（如果别人持有就阻塞等待）
// ... 临界区 ...  ← 同一时刻只有一个线程在这
m.unlock();     // 释放锁

// 推荐：RAII 风格，自动释放
{
    std::lock_guard<std::mutex> guard(m);
    // 临界区
}  // 离开作用域自动 unlock，即使抛异常也不会死锁
```

## 自旋锁 (Spinlock)

```cpp
// 自旋锁：不阻塞，反复检查锁是否可用
while (!try_lock()) {
    // 循环等待（"自旋"），消耗CPU但不切换上下文
}
```

| | 互斥锁 Mutex | 自旋锁 Spinlock |
|---|---|---|
| 等不到锁时 | 线程休眠，让出CPU | 循环检查（忙等），不放弃CPU |
| 开销 | 上下文切换开销大 | 自旋消耗CPU |
| 适用 | **临界区执行时间长** | **临界区极短**（几行代码） |

## 读写锁

```cpp
// 读可以并发，写必须独占
std::shared_mutex rw;
rw.lock_shared();    // 读锁，允许多个读者同时持有
rw.lock();           // 写锁，独占，等所有读者释放
```

## 条件变量

```cpp
// 线程等待某个条件
std::mutex m;
std::condition_variable cv;
bool ready = false;

// 等待线程
std::unique_lock lock(m);
cv.wait(lock, []{ return ready; });  // 等待直到 ready = true

// 通知线程
{
    std::lock_guard lock(m);
    ready = true;
}
cv.notify_one();  // 唤醒一个等待线程
```

# 08 CAS与Atomic

## CAS (Compare-And-Swap)

**CAS = "比较并交换"，是原子操作的基础。**

```cpp
// CAS 的语义（一条CPU指令完成，不可中断）：
bool CAS(int* addr, int expected, int new_value) {
    if (*addr == expected) {
        *addr = new_value;
        return true;   // 交换成功
    }
    return false;      // 值变了，不交换
}
```

**用 CAS 实现无锁的 counter++：**

```cpp
void atomic_increment(int* counter) {
    do {
        int old = *counter;          // 读取当前值
        int new_val = old + 1;       // 计算新值
        // 如果counter没变，换成新值；变了就重试
    } while (!CAS(counter, old, new_val));
}
// 没有锁！多个线程同时执行也没问题，CAS保证最终正确
```

## Atomic 原子操作

```cpp
#include <atomic>

std::atomic<int> counter(0);

counter++;              // 原子自增，等同于上面的 CAS 循环
counter.fetch_add(1);   // 等价写法
int val = counter.load();  // 原子读
counter.store(10);         // 原子写
```

## CAS 的 ABA 问题

```
线程A: 读到值 A
线程B: A → B → A（改成B又改回A）
线程A: CAS，发现还是A → 认为没被改过 → 实际上已经被改过了！

解决：加版本号。node是A(version1) → B(version2) → A(version3)
```

# 09 Memory Barrier

## 为什么需要内存屏障？

CPU 和编译器会对指令**重排序**以提高性能：

```cpp
// 你写的代码：
x = 1;
flag = true;

// CPU 可能实际执行：
flag = true;
x = 1;  // 被重排序了！

// 另一个线程看到 flag=true 时，x 可能还是 0！
```

## 内存屏障做什么？

**内存屏障 = 告诉 CPU/编译器："这条线不能跨过去重排序"。**

```cpp
x = 1;
atomic_thread_fence(memory_order_release);  // 写屏障：上面的写不能跑到下面
flag = true;
```

## 四种内存序（C++11 memory_order）

| 内存序 | 含义 | 用在哪 |
|--------|------|--------|
| `relaxed` | 不保证顺序，只保证原子性 | 纯计数器 |
| `acquire` | **读屏障**：后续读写不能重排到此之前 | `lock()` 的读 |
| `release` | **写屏障**：之前写不能重排到此之后 | `unlock()` 的写 |
| `seq_cst` | 全局顺序一致性，最强 | **默认，最安全** |

> **你日常直接用 `std::atomic` 的默认 `seq_cst` 就够了。只有极致性能优化时才精细调。**

# 10 死锁

## 死锁的四个必要条件

```
线程A: 持有锁1，等锁2
线程B: 持有锁2，等锁1

→ 互相等待 → 永远无法继续 → 死锁

四个条件（缺一不可）：
① 互斥：资源不能被共享
② 占有并等待：占着一个，等着另一个
③ 不可抢占：不能强行抢别人的资源
④ 循环等待：A等B，B等A，形成环
```

## 如何解决死锁

| 方法 | 破坏哪个条件 | 做法 |
|------|------------|------|
| 一次性分配所有资源 | ② 占有等待 | 要么全拿，要么一个不拿 |
| 可抢占 | ③ 不可抢占 | 拿不到就释放已有的 |
| **按序加锁** | ④ 循环等待 | **所有线程按相同顺序加锁，最实用** |
| try_lock | - | 拿不到就放弃，稍后重试 |
| 死锁检测 | - | 定期检测，发现就回滚/重启 |

```cpp
// ✅ 按序加锁：总是先 A 后 B
lock(A);
lock(B);
// 临界区
unlock(B);
unlock(A);

// ❌ 线程1先A后B，线程2先B后A → 死锁风险！
```

# 11 虚拟内存

## 物理地址 vs 虚拟地址

```
每个进程看到的是"虚拟地址空间"，不是真实物理内存。

进程A看到的：                   进程B看到的：
┌────────────┐                 ┌────────────┐
│ 0x000...   │                 │ 0x000...   │
│   ...      │   MMU(硬件)     │   ...      │
│ 0xFFFF...  │   ──映射──→     │ 0xFFFF...  │
└────────────┘                 └────────────┘
       ↘          物理内存          ↙
        ┌─────────────────────┐
        │ 真实的RAM（只有一份）│
        └─────────────────────┘
```

## 虚拟内存的三大作用

| 作用 | 说明 |
|------|------|
| **缓存** | 把磁盘当大缓存，物理内存只放活跃数据 |
| **内存管理** | 每个进程有独立的地址空间；简化链接加载；物理内存可以不连续 |
| **内存保护** | 每个进程只能访问自己的页，不能越界 |

## 虚拟地址到物理地址的翻译

```
虚拟地址 = [虚拟页号 VPN] [页内偏移]
              ↓ 查页表
物理地址 = [物理页号 PPN] [页内偏移]
```

# 12 分页

## 分页是什么？

**分页 = 把虚拟内存和物理内存都切成固定大小的"页"，以页为单位映射。**

```
虚拟内存：                 物理内存：
┌──────┐                   ┌──────┐
│ 页0  │──────────────────→│ 页2  │ ← 虚拟页0映射到物理页2
├──────┤                   ├──────┤
│ 页1  │──→ 磁盘            │ 页3  │ ← 虚拟页3映射到物理页3
├──────┤    (不在物理内存中)  ├──────┤
│ 页2  │────────────┐       │ 页1  │ ← 虚拟页2映射到物理页1
├──────┤            │       ├──────┤
│ 页3  │────────┐   │       │ 页0  │
└──────┘        │   └──────→└──────┘
                └──────────→
                   虚拟页可以映射到任意物理页，不需要是连续的！
```

## 页表

每个进程都有一张**页表**，记录"虚拟页→物理页"的映射。存在物理内存中，由 MMU（内存管理单元）硬件查询。

## 页表条目 PTE 的结构

```
一个 PTE(Page Table Entry)：
┌──────┬───┬───┬───┬──────────────────────┐
│ 物理 │   │   │   │                      │
│ 页号 │...│脏位│访问位│ 权限位(r/w/x)      │
└──────┴───┴───┴───┴──────────────────────┘
              │    │
  脏位=1：页面被修改过，换出时要写回磁盘
  访问位=1：最近被访问，LRU淘汰时参考
```

## 多级页表

```
为什么需要多级？ 64位系统地址空间巨大，单级页表太大！

一级页表（小，一直在内存）
  └→ 二级页表（按需在内存，不用的放磁盘）
       └→ 物理页

Linux 使用四级页表：PGD→PUD→PMD→PTE→物理页
```

## 写时复制 (Copy-On-Write)

```
fork() 后：
  父进程和子进程共享同一物理页
  页表标记为"只读"

  有人要写 → 触发缺页异常 → 复制该页 → 各自拥有独立副本
  
  好处：如果从不写入，就永不复制，大幅节约内存
```

# 13 TLB

## TLB 是什么？

**TLB = Translation Lookaside Buffer（快表）。CPU 内部的高速缓存，缓存最近的"虚拟页→物理页"翻译结果。**

```
CPU 访问虚拟地址：
  1. 先查 TLB → 命中 → 直接拿到物理地址，极快！
  2. TLB 未命中 → 查页表（在内存中）→ 慢 → 把结果缓存到 TLB

TLB 是 MMU 内部的硬件缓存，容量很小（几十到几百条）
```

## 为什么需要 TLB？

```
每次内存访问都要查页表？太慢了！

一次内存访问 = 读内存 = 约 100ns
一次 TLB 命中 ≈ 额外 0.5ns（几乎可以忽略）

TLB 命中率通常 > 99%，这就是虚拟内存几乎不影响性能的原因。
```

## TLB 与进程切换

```
进程切换 → 切换地址空间 → TLB 全部失效（flush）！

这就是进程切换比线程切换慢的重要原因之一。
线程切换不需要 flush TLB（同一进程共享地址空间）。
```

# 14 Cache

## CPU Cache 是什么？

**CPU Cache = CPU 内部的高速小容量存储器，用于缓存从内存读取的数据。**

```
速度金字塔：
  寄存器    ~0.5ns   (CPU内部，最快，最少)
  L1 Cache  ~1ns     (每个核独立，32KB)
  L2 Cache  ~5ns     (每个核独立，256KB)
  L3 Cache  ~20ns    (多个核共享，8~32MB)
  内存      ~100ns   (DRAM)
  磁盘      ~10ms    (最慢，最大)
```

## 缓存行 (Cache Line)

**CPU 不是按字节读内存的，而是一次读一整行（通常 64 字节）。**

```
你读 int a（4字节） → CPU 把 a 所在的整行 64 字节都加载进 Cache
紧接着读 a 旁边的 b → Cache Hit！已经在了

这就是为什么：
  vector<int> 遍历：极快（连续内存，Cache友好）
  list<int>   遍历：慢（节点分散，Cache Miss满天飞）
```

## Cache 一致性

多核 CPU 各有一份 L1/L2 Cache，如何保证数据一致？

```
核1 Cache:  x = 5     核2 Cache:  x = 5
核1: x = 10           核2: 读 x → 还是 5？错误！

解决方案：Cache 一致性协议（MESI）
  Modified  - 已修改，其他核的副本无效
  Exclusive - 独占，和内存一致
  Shared    - 共享，多核都有副本
  Invalid   - 无效，不能使用
```

# 15 页面置换算法

当物理内存满了、又要加载新页时，需要赶走一页。

| 算法 | 思路 | 特点 |
|------|------|------|
| **OPT** (最优) | 淘汰未来最久才用的页 | 理论最优，但是无法实现（无法预知未来） |
| **FIFO** | 淘汰最早进来的页 | 简单，但可能淘汰热点页 |
| **LRU** | 淘汰最近最少使用的 | **最常用**，效果好但实现开销大 |
| **LFU** | 淘汰访问次数最少的 | 历史高频但已不用的页难淘汰 |
| **Clock** (时钟) | 环形队列 + 访问位，类似简化版LRU | **Linux实际使用**，近似LRU但实现简单 |

## LRU vs Clock

```
LRU：记录精确的"上次访问时间" → 选最久的 → 开销大
Clock：
  维护环形链表 + 访问位
  扫描时针：
    访问位=0 → 淘汰
    访问位=1 → 置0，跳过（给一次机会）
  近似LRU，实现简单，Linux实际使用
```
